# Contributing

Armada welcomes contributions of all kinds — bug reports, feature requests, documentation
improvements, and code changes. If you would like to get involved, feel free to reach out
in [GitHub Discussions](https://github.com/armadakv/armada/discussions),
raise an issue, or open a pull request.

## Request For Comments

For most of the changes, the normal pull request workflow is sufficient. However, some significant changes
should go through a design process and consensus must be reached among maintainers. For this purpose, we have
the **Request For Comments** process. RFC should be drafted for example when:

* introducing a new feature or an API,
* redesigning internals in a major way,
* or considering breaking changes.

When drafting an RFC, follow the [template](proposals/000-rfc-template.md) and create a pull request to start the discussion.
The pull request should be tagged with the label `proposal`.

* [Go](https://golang.org/) >= 1.22

## Development Workflow

### Build

```bash
# Build only the armada binary (fast iteration)
make armada

# Regenerate protobuf outputs and build the binary (full build)
make build

# Regenerate protobuf outputs only
make proto
```

### Test

```bash
# Run the full test suite with race detection and coverage
make test

# Run tests for a single package
go test ./storage/table/...

# Run a single named test
go test ./storage/table/... -run '^TestTableManager$'
```

### Lint & format

```bash
# Run the linter (runs make proto first)
make lint

# Auto-format the code with golangci-lint
make fmt
```

### Run locally

```bash
# Start a single-node leader cluster in development mode
make run

# Start a follower connected to the local leader (requires make run to be running)
make run-follower
```

## Release notes

Release notes are generated by [git-cliff](https://git-cliff.org) from the titles of merged pull requests
(configuration in `cliff.toml`), so the title of your pull request is what users read in the [changelog](changelog.md).

* Start the title with a [conventional commit](https://www.conventionalcommits.org) type: `feat`, `fix`, `perf`,
  `refactor`, `docs`, `test`, `build`, `ci` or `chore`, optionally with a scope, for example `fix: bound max QUIC frame size`.
  A workflow checks the title.
* Mark anything that breaks compatibility (storage format, wire protocol, API, configuration) with `!`, for example
  `feat!: change the key layout`, and explain the upgrade path in the description. Only a `!` title lands in the
  "Breaking changes" section.
* Security fixes land in the "Security" section when the title mentions `security`, a `CVE-` or `GHSA-` id, or uses
  `fix(deps):`. Dependabot titles do not, so retitle a Dependabot PR that fixes a vulnerability.
* Use a title that describes the change for users. A `fix:` title lands under "Bug fixes" whatever the diff contains.
* Merge pull requests with a merge commit, the notes are built from "Merge pull request #N" commits. Squash merges and
  direct pushes to `master` are not picked up and the release workflow fails when it finds no entries.
* Merge each pull request of a stack into `master` individually. Commits that reach `master` inside another PR are not
  lost, they are listed under "Other commits" with a commit link instead of a PR link.

To preview the notes for the next release run `git-cliff --config cliff.toml --unreleased`.

### Cutting a release

1. Push a `vX.Y.Z` tag. The release workflow builds the binaries and images, and generates the notes from the tag
   once. A tag with a `-` such as `v0.3.0-rc.1` produces a pre-release and no changelog pull request.
2. A **draft** GitHub release is created with the generated notes. Add "About this release", the highlights and the
   upgrade notes by hand (see the earlier releases for the style), then publish it. Publishing rebuilds the docs site.
3. The workflow opens a `docs: changelog for vX.Y.Z` pull request that adds the same generated section to
   [`docs/changelog.md`](changelog.md). Copy your edits into it and merge it, which rebuilds the docs site.
   Re-running the workflow does not add the section twice, and an `## Unreleased` section is replaced.

The changelog pull request needs a one-time setup. Store a GitHub App token or a fine-grained PAT with
`contents: write` and `pull-requests: write` on this repository as the `RELEASE_BOT_TOKEN` secret.
A pull request opened with the default `GITHUB_TOKEN` does not trigger the required checks and cannot be merged.
If the checks are still missing, close and reopen the pull request.

## Running Documentation Site Locally

This documentation site is powered by [Jekyll](https://jekyllrb.com).
First, install Jekyll and [bundler](https://bundler.io):

```bash
gem install bundler jekyll
```

Then, install the necessary gems:

```bash
cd ./docs
bundle install
```

Last, run Jekyll in the root of the repository:

```bash
make serve-docs
```
